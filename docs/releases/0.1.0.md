# SupportAgent 0.1.0: the first public release

> **Released 2026-11-20 by maintainer decision, ahead of the partner-dependent v0.1 exit criteria.** The code for every v0.1 work package is merged, and so are the modular framework, system onboarding and transaction tracing. Two v0.1 exit criteria are still open because they need a design partner's data: the quality gates on the holdout and the shadow promotion gate (ROADMAP §3, v0.1). See **Release checklist** and **Known limitations**. 0.0.0 was never tagged; its scope ships here.

SupportAgent is a self-hosted operations agent, licensed Apache-2.0. It watches a ticketing system (ServiceNow, or any source through the generic webhook), triages each incident, investigates it with read-only tools, and proposes what a person should do next. It never acts without either a human approval or a grant a human approved, and the database enforces that (INV-01).

## What 0.1.0 does

- **Triage (Loop A):** it polls ServiceNow under a DB lease, deduplicates (INV-02), pre-classifies and classifies through the redacting LLM boundary (INV-06), groups storms, and routes on a signed, per-model calibration table. Anything uncertain gets a safe default.
- **Modes:** `shadow` records what it would have proposed and sends nothing. `assisted` (ADR-0008) sends what a human approves, plus what an approved grant covers. That includes SOP steps on auto, under conditions that must hold every time (ADR-0014).
- **Investigation:** skill packs (labels, hypotheses, checks) for python-postgres, oracle, java-spring, kubernetes, kafka, mongodb, nodejs, rabbitmq, snowflake, spark, streamlit and data-quality. Read-only tools and MCP servers (metrics, Loki logs, Postgres, Oracle). Knowledge from Git markdown and Confluence. RCA-lite, where every claim must pass the `entail` check and an unsupported claim is dropped, never shown.
- **Onboarding (ADR-0015 to ADR-0020):** `supportagent onboard run` drives onboarding for any system. It detects the stack, installs plugins (which are data, ADR-0016), builds the system graph and incident map, and asks for read-only access where it needs it. It fits calibration from the system's own history, and readiness is gated per incident class by shadow replay.
- **Transaction tracing (ADR-0021):** `supportagent trace` and `/ui/trace` follow one business object through a reviewed flow. Logs come first, and reviewed `records.query` SELECTs are used where logs can't establish a stage. PII is pseudonymised by Presidio, failing closed. The answer is a cited timeline that names the first deviation.
- **Operations:** `./install.sh` sets up a local install with Keycloak and a demo ServiceNow. Also included: `doctor`, `replay`, `stats` with the counterfactual baseline, Litestream, an observability stack (Prometheus, Loki, Alloy, Grafana, mcp-grafana), and OIDC login with RBAC. Sign out also ends the IdP session.

## Known limitations

- **No holdout-grade calibration ships.** Until a deployment fits or writes its own calibration, every incident safe-defaults: it is classified, but not routed with confidence (`doctor` warns). A smoke-grade table can't route either: a perfect 12/12 scores 0.758 under the Wilson lower bound, below `min_score` 0.80 (ADR-0002).
- BL-038: no change source yet, so `recent_change_push` is at best inconclusive.
- BL-041: assisted mode applies to every catalog service. There is no treatment/control split yet.
- BL-023: login is tested against a mock IdP and runs on the local install's Keycloak; the staging run against a real IdP is part of the open exit demo.
- BL-033: comms plans are customer plans only. BL-049: MCP over streamable HTTP only, no stdio.
- Transaction tracing is generic. The first flow on a real system is being fitted (BL-056).
