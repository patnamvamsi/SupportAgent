Blueprint · an application support agent framework

The LLM decides content. Code decides control.

SupportAgent triages incidents and investigates their root causes the way a support analyst does: it reads the ticket, pulls evidence from the systems behind the service, and proposes what to do. A fixed trust core enforces every guarantee. Knowledge about each technology stack, the tools it can query, the incident system it works in and the documentation it can read all plug in around that core. They add capability, never authority.

A fixed trust core with four plug-in layers

Everything that decides whether something may happen is in the core. Everything that decides what the agent knows and can see is a plug-in. That split is what lets the framework support a Postgres web app, a Spark pipeline or a Java service without weakening any guarantee.

How an incident moves through the system

A linear triage loop, then one budgeted investigation loop. Every stage writes an event, so replay <trace> shows the whole path, and every stage that can fail has a named safe default that hands the case to a human.

The trust core: six guarantees, each with a test

These are the only things SupportAgent claims. Each has a test ID that must pass in CI on both SQLite and Postgres. If a test can't be written, the guarantee isn't claimed.

INV-01 · authorization

No unapproved action

A write executes only if its outbox row points at exactly one valid authorization: a single-use approval matching the payload hash, an in-scope policy grant, or an approved comms plan. Database triggers enforce it.

INV-02 · dedup

One case per fingerprint

Duplicates increment a counter; a severity escalation re-triages the same case in place. A partial unique index enforces it.

INV-03 · trace

Everything is an event

Every side effect, LLM call, tool call and decision is an append-only event with a trace id, so any case can be replayed.

INV-04 · idempotency

Effectively-once sends

Re-running a send with the same key is a no-op: a marker on every note plus read-before-write reconciliation.

INV-05 · failure

Fail to a human, not a crash

Any LLM, tool or config failure ends in a safe default with zero unapproved side effects.

INV-06 · redaction

No secrets reach a model

Redaction runs inside the only path to an LLM provider, so no call site can skip it. A canary corpus proves it.

Root cause analysis: a plan of checks, not a chat

The investigation tests declared hypotheses with machine-checkable evidence. The LLM may suggest which hypotheses to test, but it may only pick from the active packs, and it never grades its own conclusion.

Skill packs: what the agent knows, per technology stack planned · WP-M01

A Postgres web app, a Spark job and a Java service fail in different ways. A skill pack bundles one stack's failure knowledge. A catalog service declares its stack, and only the matching packs reach the prompts and the plan, so the model sees "connection pool exhaustion in the app's pool" instead of six generic guesses.

Connectors: the incident system is a plug-in planned · WP-M07

ServiceNow is the first connector, and it is battle-tested against a real instance. The core will speak a normalized model, so a second system (Jira Service Management, Zendesk, PagerDuty or Opsgenie incidents) doesn't touch triage, the gate or takeover. Knowledge: documentation as guidance, never as evidence reserved · WP-M08

Teams keep runbooks and procedures in Git, Confluence or SharePoint. The agent will retrieve them to guide an investigation or a request, under five rules that keep a stale or hostile page from steering it.

  1. Guidance, not evidence. A doc can raise a hypothesis and suggest a check. SUPPORTED still needs tool evidence; a doc-only claim is labelled "documented guidance".
  2. No authority. A procedure maps onto the existing typed actions, and each one passes the gate. Doc text is never executed.
  3. Untrusted input. Docs are redacted at ingest and handled like log text, with injection canaries in the evals.
  4. Cited and replayable. Each chunk carries page, version, URL, owner and a content hash; the trace records what was read.
  5. Scoped by pack and service. Visibility follows the doc, so an internal page never reaches a customer draft.

Extend it without being a developer planned · WP-M09

A support analyst who spots a gap describes it in plain language to a coding harness, ideally with a real incident or two. The harness proposes a pack change, a tool or an MCP binding that fits the framework, proves it in the lab, and opens a pull request. The analyst doesn't need to learn the framework.

Humans stay in control

Trust is earned in stages, and a person can always take the case back.

Shadow → assisted → standard

Shadow records what the agent would have done and sends nothing. Assisted acts within grants and approvals (built in v0.1, ADR-0008). Standard comes later. Promotion is a human decision informed by agreement stats.

Approvals with identity

Approvers sign in through your identity provider (OIDC with PKCE). An approval is single-use and bound to the payload hash the approver saw; nobody approves their own proposal.

Takeover

When a person changes the assignee or status, the case becomes human-owned: the agent stops proposing and sending, and turns due updates into drafts for the owner.

Customer comms plans

One approval covers a cadence of updates from a fixed template. Fields come only from values a person set, including when they raised the ticket (ADR-0010), never from model inference.

Severity from the source

Severity routes on the incident system's priority (ADR-0009), with the model's guess only as a fallback. A raised priority re-triages the case.

Replay anything

supportagent replay <trace> prints every step: what was read, what the model returned, what was decided, who approved, what was sent.

Evals: reliability measured in six layers

The system's outputs are typed: a label, a severity, hypothesis ids, a verdict, cited evidence. So most evals are scored deterministically against ground truth, with no model grading another model. The false-cause rate, a confident wrong root cause, has the strictest gate.

Scenarios include distractors, cases with no findable cause (the right answer claims none), prompt injection in logs and docs, and a held-out split never used for tuning. A pack can't be enabled for assisted mode until it passes its gates.
