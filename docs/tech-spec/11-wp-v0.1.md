## WP-101 Case lifecycle, takeover, hand-back

- **Spec refs:** ARCH §8.1, §8.2; 01 §7.11; 02 §2 (hand-back); 03 §2.5 (`automation_actors`).
- **Deliverables:** `domain/takeover.py` (`is_human_actor(actor, integration_user, automation_actors) -> bool`; `detect_takeover(changes, ...) -> TakeoverSignal | None`: a human actor changing `assigned_to` or `state`), `app/lifecycle.py` (`LifecycleService.apply(case_id, changes)`, using CAS transitions), `InboundHandler.on_changes` bound to it, `entrypoints/api/routes/cases.py` (hand-back), a "Hand back" button in the case view, `doctor --discover-automation` admin confirmation UI (`/ui/setup` panel), owner-draft rendering hook (used by WP-102).
- **Behaviour:** state changes from ServiceNow map to lifecycle events (`resolved`/`closed` → `resolved`; `reopened` state value → `reopened`). On takeover: transition to `human_owned`, emit `sync_takeover {actor, field, sys_mod_count}`, supersede every `pending_approval` proposal for the case (`case_retriaged` → `superseded`), and block new submits (`GateService.submit` checks the case status and returns `Skipped(reason="human_owned")`). `mode: assisted` requires every automation-actor candidate to be confirmed or rejected (a config validation error otherwise).
- **Tests first:** `test_sync_human_change_behind_echo_detected`, `test_sync_automation_assign_not_takeover`, `test_takeover_supersedes_pending_proposals`, `test_human_owned_blocks_new_submits`, `test_hand_back_api_transitions_to_in_progress`, `test_hand_back_by_reassign_to_integration_user`, `test_new_alert_while_human_owned_is_duplicate_not_hand_back`, `test_resolved_then_reopened_lifecycle`, `test_assisted_mode_requires_confirmed_automation_actors`.

## WP-102 Comms plans, renderer, cadence

- **Spec refs:** ARCH §6.3; CAP §4.1; 01 §7.4, §7.12.
- **Deliverables:** `domain/comms.py` (`AllowedField(name, source: Literal["record_state","schedule"])`, `PlanSpec`, `plan_hash()`, `render(template, fields) -> str`; rendering fails if any template variable isn't an allowed field or a fixed literal), `templates/comms/*.txt.j2` (customer and internal templates; `StrictUndefined`), `app/comms.py` (`CommsPlanner.plan(case, route.comms) -> Proposal` of kind `comms_plan`; `CadenceJob.run(now)`: for each approved plan of an active case, compute `interval_slot`, read field values **from the latest human-actor change in the per-change history** (`record_state`) or the schedule, render, and enqueue an outbox row with `comms_plan_id` and the idempotency key from 01 §7.4; under `human_owned`, store an owner draft instead), plan-approval UI on the case view.
- **Behaviour:** a `state` value written by the integration user is **never** a valid `record_state` source; only human-actor values count. A plan whose case is resolved moves to `satisfied` after the final "resolved" update.
- **Tests first:** `test_plan_autosend_fields_from_record_state`, `test_plan_rejects_agent_source_field`, `test_plan_hash_changes_when_template_changes`, `test_cadence_one_send_per_slot`, `test_cadence_missed_slot_not_backfilled`, `test_cadence_human_owned_creates_draft_not_send`, `test_comms_plan_revoked_blocked` (end-to-end through the outbox), `test_render_rejects_unknown_variable`, `test_resolved_case_satisfies_plan`.
