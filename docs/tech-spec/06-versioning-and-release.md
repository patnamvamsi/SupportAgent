# 06. Versioning and Release

Every artifact that can change behaviour has a version, and the version appears in the events it influences, so any decision can be traced back to the exact code, config, prompt, taxonomy, calibration and model that produced it (INV-03).

---

## 1. Application version (SemVer)

`supportagent` follows **SemVer 2.0** with pre-1.0 semantics: in `0.MINOR.PATCH`, MINOR is a roadmap release and PATCH is a fix within it.

| Roadmap release | Version line | Git tag | Weeks |
|---|---|---|---|
| v0.0 walking skeleton | `0.0.x` | `v0.0.0`, `v0.0.1`, … | 1–4 |
| v0.1 trustworthy core | `0.1.x` | `v0.1.0` | 5–12 |
| v0.2 support analyst with hands | `0.2.x` | `v0.2.0` | 13–18 |
| v0.3 = **v1.0** | `1.0.0` | `v1.0.0` | 19–24 |

The version is single-sourced in `pyproject.toml` and exposed as `supportagent.__version__`, in `/readyz` and in every `ingest` event (`payload.app_version`). Pre-release builds use `0.1.0rc1` etc.

## 2. Database schema

- Alembic revision numbers encode the release that introduced them (`00xx` v0.0, `01xx` v0.1, `02xx` v0.2, `03xx` v0.3; 03 §4).
- On startup, if the DB is not at head, `/readyz` fails and the worker refuses to run (`supportagent migrate` must run first). The app never auto-migrates in production.
- A release may only add migrations. Released revisions are immutable; fix forward.
- Every release tag records its head revision in `docs/releases/<version>.md`.

## 3. Data contracts

| Artifact | Version field | Rule |
|---|---|---|
| `supportagent.yaml` | `config_version: 1` | Additive changes keep the version. A breaking change bumps it, ships a `supportagent config migrate` step, and the loader rejects unknown versions |
| `taxonomy/classification.yaml`, `taxonomy/hypotheses.yaml` | `version: MAJOR.MINOR.PATCH` | Add a label = MINOR; rename or remove = MAJOR (needs routing, runbook and eval updates in the same PR); a description fix = PATCH. Recorded in `classify` events |
| `catalog/services.yaml` | `version:` (customer-owned, free-form) | Recorded in `decision_json.catalog_version` |
| Action kinds (`domain/kinds.py`) | tied to the app version | A new kind needs a migration that regenerates trigger literals and CHECK lists |
| Event payloads | `payload.v` per kind (int) | Readers handle all versions ≥ 1. Never reuse a version number |
| HTTP API | `/api/v1` path | Breaking change = `/api/v2`, with v1 kept for at least one minor release |

## 4. Prompts, models, calibration and eval snapshots

| Artifact | Identity | Rule |
|---|---|---|
| Prompt | `prompts/<slot>/v<N>.md` + rendered-prompt hash | Never edit a released `v<N>` file; add `v<N+1>`. A PR that adds or activates a prompt version must pass the quality suite (smoke in v0.0) |
| Model | dated snapshot id per slot | Changed only through the deprecation runbook (ARCH §9) and an ADR |
| Calibration table | `evals/artifacts/calibration.json` `version` + `grade` + `snapshot_id` + `model_id` | Regenerated by an eval run, never hand-edited (CI checks the file's signature block written by the harness) |
| Eval snapshot | `evals/snapshots/<snap-YYYY-MM-DD>/` | Immutable once referenced by a manifest; a bump is an ADR |
| Eval suite manifest | `evals/manifest.yaml` (`suite_version`, snapshot id, case list hash) | Cases are added (with `source:`), never weakened without `meta.why` |

## 5. Documentation versions

- `docs/spec/*` is frozen; changes go through ADRs (`docs/adr/NNNN-*.md`).
- `docs/tech-spec/*` carries `tech-spec MAJOR.MINOR.PATCH` in its README. A refinement pass before each release bumps MINOR (`1.1.0` before v0.1 work, `1.2.0` before v0.2 work, `1.3.0` before v0.3 work).

## 6. Release procedure

1. All WPs for the release are `done` in their WP file's status table.
2. CI is green on `main`, including the nightly soak and the eval gates for the release (v0.0: smoke + invariants; v0.1+: quality gates on the holdout).
3. Bump the version in `pyproject.toml`, and generate release notes from conventional commits into `docs/releases/<version>.md`. The notes contain: WPs delivered, migrations (head revision), config changes, prompt/model/taxonomy versions, calibration grade, known limitations.
4. Tag `v<version>`; CI builds and signs the Docker image `supportagent:<version>` (and `:<minor>` floating tag), and attaches the SBOM.
5. Run the release's exit demo (ROADMAP §3) on a staging instance against FakeServiceNow **and** a ServiceNow developer instance; record the result in the release notes.
6. Update `docs/CHANGELOG.md` only for design-level decisions (ADRs referenced), not for code changes.

## 7. Compatibility promises (pre-1.0)

- Data written by `0.N.x` is readable by `0.(N+1).x` after migration.
- Config `config_version: 1` remains valid through 1.0 unless an ADR says otherwise.
- `/api/v1` is stable from v0.1.0. In v0.0 it may change.
